# Python 下层 Agent 构建笔记

## 职责

Python 是独立的下层 Agent 服务，负责面试规划、评分、路由、出题、记忆、RAG 和模型调用。Java 只传递固定契约中的身份、会话、初始化快照和用户回答；Python 不感知上层页面或具体业务按钮。

## 面试单轮顺序

1. `InterviewEvaluationAgent` 只使用 `interview-coach` Skill 和 `evaluation.md` 评估用户回答；规划阶段选出的岗位领域 Skill 不会注入评分节点。评分维度、权重和标准只由 Skill/Prompt 定义；它只读取当前题、回答、会话记忆与生成当前题时保存的证据缓存，缓存仅用于事实核对，不能改变评分标准，也不能调用 RAG。
2. `InterviewRoutingAgent` 使用 `routing.md` 消费评分结果，根据阶段配额判断追问、下一题、下一阶段或结束，并确定 `nextTopic`；它没有知识库检索能力。
3. 读取当前会话的题目证据缓存。
4. 缓存未命中时，才按已确定的阶段和题目方向联合检索系统知识库与用户知识库。
5. 生成具体题目，并把题目证据写入缓存，供下一轮评分只读使用。

评分绝不通过检索知识库完成；RAG 检索结果不能反向决定题目方向。缓存键由阶段、标准化题目方向和当前会话选定的知识库 ID 集合组成；命中时不再请求向量库。评分、记忆、RAG 证据不出现在文本面试的 `output` 中；响应中的 `turnStage` 仅标记本次已回答问题所属阶段，供 Java 保存可见历史。

## 接口边界

会话暂停使用 `agent.session.pause` 将持久化状态置为 `PAUSED`，不结束会话或归档记忆；之后携带最新 `sessionStatus=PAUSED` 和 `stateVersion` 提交回答即可恢复为 `ACTIVE`，不会重新初始化 Agent。

前端将 `ACTIVE` 与 `PAUSED` 都识别为可继续会话：历史列表和面试首页会把两类会话带着原 `sessionId` 进入恢复页，而不是误当作只能查看的历史记录。

- `/v1/agent/sessions/initialize`：创建或恢复会话。
- `/v1/agent/respond`：提交回答并返回下一条可展示消息。
- `/v1/agent/sessions/complete`：完成或中断会话。
- `/v1/agent/resume/activate`：将真实的最新简历版本设为下层长期画像的唯一可写版本，并清除旧版简历派生画像。
- `/v1/agent/evaluate/resume`：评价简历；只有 `subjectId` 与当前激活简历一致时才写入长期画像。
- `/v1/agent/rag/index`：接收上层索引任务。
- `/v1/agent/rag/delete`：按显式知识库 ID 删除全部向量分片。
- `/v1/agent/skills`：Skill 列表与 JD 分类。

不提供独立 RAG 搜索聊天接口，也不提供面试日程解析接口。知识库检索只作为文本面试内部工具。

## RAG 资料与切分

系统基础资料位于 `python-agent/config/rag/sources/`：`java-interview-knowledge-base.md` 覆盖 Java、数据库、中间件、框架与计算机基础；`llm-interview-knowledge-base.md` 覆盖 RAG 与 Agent 面试知识。两份资料均为纯文本 Markdown，不索引图片。

下层先按 Markdown 标题切分正文：每个分片保存完整的标题路径（例如“Java 面试系统知识库基础资料 > Java 并发 > 线程池”）到向量元数据，并将该标题路径重复写入分片正文。若单个标题段超过 `rag-policy.json` 的 Token 上限，才在该标题段内部按 Token 二次切分，并使用 `sectionPartIndex` 标识段内序号。代码围栏内以 `#` 开头的注释不参与标题识别。没有 Markdown 标题的 PDF/纯文本仍退化为原有 Token 切分。

当前上层用 Apache Tika 提取上传 PDF 的文本后发送给下层；因此可复制文字的 PDF 可以索引。扫描件、图片型 PDF、复杂表格/双栏排版和 PDF 内图片没有 OCR 或版面恢复能力，不能保证正确检索，上传前应先完成 OCR 或转为结构化 Markdown。

当前题目生成检索默认召回最多 10 个、相似度阈值为 `0.35`。项目尚未接入独立 Reranker，因此这 10 个满足阈值的分片会直接作为题目生成的候选证据；后续接入 Reranker 后，应改为“较大规模召回 → 精排 → 保留少量证据”。

## 可靠性

简历激活与评估请求均使用下层长期记忆中的 `runId + 输入指纹` 快照幂等：激活重放不会再次清空已完成画像；第一次成功评估会将结构化结果与画像更新一起保存；同一 `runId` 和同一输入重试直接返回已保存结果，不重复调用大模型；同一 `runId` 携带不同简历、岗位或文本时返回一致性错误。

### 面试单轮约束补充

当前轮评分完成后，会先把问题、回答、评分和路由结果写入下层会话的短期记忆视图，再读取 RAG 缓存或检索并生成下一题。因此出题可以使用当前轮回答，但长期记忆只在完整的下一会话状态成功持久化后写入，避免 RAG 或出题模型失败时留下一个未被会话接受的长期记忆事件。

评分只依赖 `interview-coach` Skill、评分 Prompt、当前问题、回答和已保存记忆；评分节点禁止发起新的知识库检索。路由节点先消费评分并确定 `FOLLOW_UP`、`NEXT_QUESTION`、`NEXT_STAGE` 或结束动作及 `nextTopic`。只有路由确定题目方向后，题目节点才读取会话证据缓存；缓存未命中时才联合检索系统知识库和用户知识库，并将证据写入缓存。`turnStage` 表示刚回答的问题所属阶段，`currentStage` 表示处理完成后的会话阶段。

### 面试流程约束优化

- 开场 Prompt 只生成自我介绍问题；初始化阶段只保存阶段骨架，非固定阶段的题量由路由过程动态决定。
- 开场回答完成后会再次调用 Planner：将本次自我介绍追加到当前简历快照，重新生成后续阶段主题；因此正式项目深挖不会只依据上传简历的旧快照。
- Python 代码执行硬边界：单个阶段最多 4 道主问题、单个主题最多 3 次发问（主问题和追问合计）、总发题数不超过系统的 20 题预算。达到边界时自动切换阶段或结束，不依赖模型自觉遵守。
- 每道题生成后立即写入 `asked_question_catalog`、阶段计数和主题计数；回答记录保存 `topic`，后续出题可避免重复主题和重复问题。
- 长期记忆按用户和当前简历版本隔离。新简历激活时清理旧简历提取的技术栈、技术深度、偏好和分析 notes；旧版本的异步分析不能覆盖当前版本。
- 会话原始问答完整持久化，但交给模型的短期记忆只包含最近 5 轮；更早轮次按“主题、问题、回答摘要、分数”压缩为会话摘要，并在评分、路由和出题上下文中显式传递。
- 路由和出题 Prompt/Skill 同时接收当前简历画像、JD、长期画像、会话摘要、最近问答及覆盖台账。RAG 有证据时，出题 Prompt 必须使用其中知识点；阶段变化必须伴随题型变化。

模型调用使用有限重试；初始化和回答的 `runId` 都绑定真实请求内容，重放时内容不一致返回 3xx 一致性错误；会话使用版本号控制并发；持久化失败通过会话状态和后续补偿处理，逐步完善最终一致性。

参数校验失败仍返回统一 JSON 字段集。仅当请求中真实携带了 `requestId`、`runId`、`userId` 或 `sessionId` 时才回传对应值；未知值明确为 `null`，下层不得生成随机或固定占位标识。

知识库重建会先完成全部嵌入，再在向量库中替换同一知识库的数据；嵌入失败时保留旧向量。删除与索引按知识库 ID 串行化，Java 删除状态为 `DELETING` 时拒绝新索引，并清理已经迟到写入的向量。
## 面试流程新增约束

下层用 `total_question_count` 记录已发出题目（开场、主问题、追问均计入），并在 20 题处硬停止。`_allowed_actions` 在回答评估完成后才计算追问权限：评分不超过 60 或存在明确弱点才允许追问。算法阶段使用 40 分作为“严重不足”阈值，只有满足该条件才开放第二道算法题。每轮快照只向上层暴露候选人可见的评估摘要、计数和最终报告，不暴露 RAG、记忆和内部路由信息。

本轮状态机补强：PROJECT、FUNDAMENTAL、SCENARIO 达到至少 2 道主问题后只能选择继续当前阶段或 `NEXT_STAGE`，不会再把模型的 `END_INTERVIEW` 当作跳过后续阶段的快捷方式；CODING 第一题评分低于 40 分时确定性开放第二题，否则直接进入 SUMMARY。Planner 结果在代码中归一化为三个中间阶段最多 4 道主问题/每题最多 2 次追问，CODING 最多 2 道且不追问。`questionCount` 仅作为兼容字段，下层初始化始终使用系统安全预算 20，实际发题数按评分、阶段覆盖、追问上限和剩余预算动态决定。
