# Interview Agent 项目业务模块设计

本文档用于确定项目的业务模块、模块边界、技术选型和面试可展开知识点。它是具体设计文档，受 AGENT_PROJECT_RULES.md 的整体要求约束。

术语约定：

- Java 后端：负责业务数据、业务流程和前端接口的主业务服务。
- Python Agent：负责 Agent 决策、工具调用、知识检索、记忆和模型交互的智能服务。
- Tool：Agent 可以调用的具体动作。
- Skill：面向某类任务的知识和行为规则。
- MCP：连接外部资源和工具的标准化方式。
- RAG：基于外部资料的检索增强生成能力。

## 一、整体业务主线

用户上传或选择简历、岗位描述和面试知识资料，创建一次面试准备会话。Agent 根据用户目标判断是否需要读取简历、解析岗位、检索知识库或查询历史记录，然后生成问题、追问或评价。用户在前端持续交互，系统流式返回回答、来源、执行状态和最终报告。

主链路：

    资料准备 → 知识库构建 → 创建面试会话
        → Agent 判断与工具调用 → 生成问题/追问
        → 用户回答 → Agent 评价 → 形成报告

### 服务职责架构

系统采用“Java 业务服务 + Python Agent 领域服务”的职责划分：

    前端
      ↓
    Java 业务后端
      ├── 管理资料、会话、问题、回答和评价
      ├── 负责业务事务、一致性、并发、异步、失败恢复和部署治理
      ├── 向 Python 组装最小必要上下文
      └── 持久化业务结果和 Agent 运行引用
             ↓
        Python Agent 服务
          ├── 管理 Agent 运行状态、记忆、RAG 数据和工具执行记录
          ├── 执行 Agent Loop
          ├── 选择和调用 Tools、Skills、MCP
          ├── 调用模型
          └── 返回结构化事件和最终结果

Java 是业务数据的唯一管理方；Python 是 Agent 领域数据的唯一管理方。Python 服务重启后不应导致 Agent 记忆、RAG 数据、运行状态或工具记录丢失。

Python 通过 Java 提供的内部能力获取用户、会话、简历、岗位描述和业务历史；Python 自己完成记忆管理、知识检索和 Agent 执行。Java 负责提供最小必要上下文，Python 负责基于上下文作出智能决策。

最终架构决策：

- Java 是业务领域服务，负责业务数据、业务事务、业务任务和业务工程治理。
- Python 是 Agent 领域服务，负责 Agent 执行、记忆、RAG、Tools、Skills、MCP 和 Agent 运行记录。
- 两个服务可以使用同一个 PostgreSQL 实例，但必须使用独立的数据边界，不共享写入同一业务数据表。
- Java 通过 userId、sessionId 和 runId 向 Python 提供上下文；Python 使用这些标识隔离自己的记忆、RAG 和运行数据。
- Java 保存最终业务结果和 Agent 运行引用；Python 保存 Agent 执行过程和 Agent 领域数据。
- 两个服务各自实现本地必要的可靠性，跨服务通过幂等标识、状态和接口契约协作，不追求跨服务全局事务。

## 二、业务模块总览

项目划分为九个模块：

1. 面试准备资料模块
2. 知识库与 RAG 模块
3. 面试会话与面试业务模块
4. Agent 编排模块
5. Agent 能力接入模块（Tools、Skills 与 MCP）
6. 记忆与上下文模块
7. Agent 运行记录与 Harness 设计模块
8. 异步任务与可靠性模块
9. 部署与运行保障模块

其中 1、2、3 是业务基础；4、5、6、7 是 Agent 核心；8、9 用于补足工程化闭环。

## 三、模块设计

### 1. 面试准备资料模块

#### 模块职责

- 管理用户的简历、岗位描述和个人补充资料。
- 支持资料上传、解析、查看、替换和删除。
- 为一次面试会话确定使用哪些资料。

#### 可展开知识点

- 多种资料如何统一成可供 Agent 使用的文本或结构化信息。
- 原始文件、解析结果和分析结果之间的关系。
- 简历与岗位描述如何共同影响问题生成。
- 重复上传、资料版本变化和删除后的关联处理。
- 文件上传失败、解析失败和内容为空时的用户体验。

### 2. 知识库与 RAG 模块

#### 模块职责

- 管理面试知识资料和资料分类。
- 完成资料进入知识库、检索和引用的闭环。
- 为 Agent 提供可信的外部知识，而不是让模型只依赖自身记忆。
- 提供预置的面试题库和知识评价资料，用户上传的资料作为补充，而不是系统运行的前提。

#### 知识内容分类

知识库不把所有内容混成一个集合，至少区分两类内容：

题库：

- 面试问题
- 面试方向和技术主题
- 难度和适用岗位
- 考察目标
- 追问方向
- 常见错误
- 参考答案要点

知识与评价库：

- 核心概念
- 原理说明
- 常见误区
- 回答评价标准
- 优秀回答应覆盖的要点
- 不同水平的回答特征

题库主要用于出题、追问和题目去重；知识与评价库主要用于解释原理、评价回答和生成改进建议。

#### 可展开知识点

- 资料处理、清洗、切分、索引和检索的完整链路。
- 分块粒度、召回数量、相关性和上下文长度之间的权衡。
- 如何把题库、评价知识、简历和岗位描述区分处理。
- 检索结果如何回传来源，帮助前端展示依据。
- 检索不到内容时如何降级，如何减少无依据回答。
- 如何评价 RAG 质量：召回效果、回答相关性、延迟和成本。
- 如何为题库和知识与评价库设计不同的检索条件和结果格式。

这是建议重点深入的模块之一。

### 3. 面试会话与面试业务模块

#### 模块职责

- 创建、暂停、继续和结束面试会话。
- 管理面试阶段、问题、用户回答、追问和评价。
- 生成面试总结和可查看的结果报告。

#### 可展开知识点

- 一次面试会话的状态流转。
- 问题生成、用户回答、追问和评价之间的业务关系。
- 如何避免同一会话重复出题。
- 如何将结构化评价转换成前端可读的反馈。
- 如何区分实时反馈和面试结束后的总结评价。
- 文字面试和未来语音面试如何共用业务模型。

### 4. Agent 编排模块

#### 模块职责

- 接收用户目标并决定下一步行动。
- 编排问题生成、资料读取、知识检索、回答评价等能力。
- 管理一次 Agent 运行的状态、步骤、终止和异常。

#### 可展开知识点

- Agent 与普通问答、固定工作流的区别。
- Agent Loop：理解目标、决定行动、执行工具、观察结果、继续或结束。
- Agent 如何判断当前应检索题库、知识与评价库、简历、岗位描述或历史记录。
- Agent 如何基于检索到的题目进行选择、改写或组合，而不是简单随机出题。
- Agent 如何基于候选人的回答检索相关知识点和评价标准，再决定追问、补充或切换主题。
- 什么时候应该让模型自主决策，什么时候使用确定性流程。
- 如何设置最大执行步骤、超时和终止条件，防止循环。
- 如何处理工具结果不完整、模型输出不符合预期或任务目标不清晰。
- 如何在可控范围内使用 Agent，而不是让模型拥有无限权限。

这是项目最核心的 Agent 模块，也是建议重点深入的模块。

### 5. Agent 能力接入模块：Tools、Skills 与 MCP

#### 模块职责

- 统一管理 Agent 可以使用的能力。
- 将业务能力包装为 Agent 可理解、可调用和可追踪的工具。
- 使用 Skill 保存不同面试方向的知识、规则和行为约束。
- 通过 MCP 连接外部或独立的能力服务。

#### 可展开知识点

- Tool、Skill、MCP 的职责区别：
  - Tool 是可执行的具体动作。
  - Skill 是面向某类任务的知识和行为规则。
  - MCP 是连接外部资源和工具的标准化方式。
- 工具输入输出如何结构化，如何进行参数校验。
- 工具设计应保持原子、可解释、可失败和可审计。
- Skill 如何按面试方向加载，避免所有知识长期塞入上下文。
- MCP 适合解决哪些外部能力接入问题，以及与直接注册工具的差异。
- 将题库检索和知识评价检索分别封装为 Agent 可调用的能力。
- 工具调用失败时如何返回可理解的错误，而不是让 Agent 无限制重试。
- 工具权限、敏感操作和提示注入的基本边界。

首期不要求建设复杂的 MCP 生态，但必须能说明 MCP、Skill 和 Tool 的关系，并保留一个可演示的接入场景。

### 6. 记忆与上下文模块

#### 模块职责

- 保存当前面试会话中的短期上下文。
- 保存可跨会话复用的用户面试信息和历史结果。
- 在有限上下文范围内为 Agent 提供最相关的信息。

#### 可展开知识点

- 短期记忆、长期记忆和工作状态的区别。
- 当前对话、用户简历、历史问题和评价结果分别放在哪里。
- 上下文过长时如何裁剪、摘要、筛选或重新检索。
- 如何避免把无关历史内容持续注入模型。
- 记忆更新的时机，以及错误记忆如何修正或删除。
- 记忆对个性化面试体验的价值与隐私边界。

面试 Agent 的记忆和 RAG 需要分工：

- RAG 提供可复用的题目、知识和评价依据。
- 记忆保存当前候选人的会话过程、已问问题、回答表现和个性化信息。
- Agent 将两者结合，决定下一步考察内容。

### 7. Agent 运行记录与 Harness 设计模块

#### 模块职责

- 记录一次 Agent 运行经历了哪些步骤、调用了哪些工具、使用了哪些资料以及最终结果。
- 提供调试、复盘、质量评估和后续优化的基础。

#### 可展开知识点

- Harness 的基本思想：模型之外的提示、工具、状态、编排、约束、观测和恢复机制。
- 如何把 Agent 的运行过程做成可追踪的事件，而不是只保存最终答案。
- 如何区分用户可见信息、开发调试信息和不应暴露的内部信息。
- 如何记录模型调用次数、工具耗时、失败原因、检索来源和最终质量。
- 如何基于运行记录分析幻觉、循环、错误工具选择和延迟问题。
- 如何设计离线评估样例，比较不同 Prompt、检索策略或工具策略。

Harness 在本项目中可以先作为架构思想和运行记录设计体现，不要求实现完整的平台。

### 8. 异步任务与可靠性模块

#### 模块职责

- 处理不适合同步等待的资料解析、知识库构建、批量评价和报告生成任务。
- 统一管理任务状态、重试、失败和恢复。

#### 可展开知识点

数据一致性：

- 文件、资料记录、解析结果、向量索引和任务状态之间的一致关系。
- 数据库更新成功但异步任务未创建、任务重复执行或任务执行后结果未落库等场景。
- 如何通过明确的状态流转、幂等处理和结果校验降低不一致。
- 删除或替换资料时，如何处理旧任务、旧索引和旧结果。

并发问题：

- 同一会话同时提交多个回答或同时触发多个 Agent 运行。
- 同一资料被重复解析、重复向量化或重复评价。
- 多个用户同时使用模型、检索和任务队列时的资源限制。
- 如何避免重复提交、状态覆盖、数据竞争和无止境的并发增长。

服务失败处理：

- 模型超时、模型限流、工具不可用、向量检索失败和数据库短暂不可用。
- 哪些错误可以重试，哪些错误应立即失败。
- 重试次数、退避、降级回答、任务恢复和用户提示。
- Agent 中断后如何保留已完成步骤，并支持重新执行或继续执行。

任务异步处理：

- 哪些工作必须同步返回，哪些工作应转为后台任务。
- 如何让前端查看任务进度、失败原因和最终结果。
- 任务重复投递、任务超时、任务取消和失败任务重新处理。
- 如何让异步任务和面试会话状态保持可解释的关系。

这是工程化部分的核心模块。

### 9. 部署与运行保障模块

#### 模块职责

- 让完整系统能够在虚拟机中启动、访问、验证和演示。
- 统一处理运行环境、服务依赖、配置、日志和基础恢复能力。

#### 可展开知识点

- 多服务启动顺序和依赖检查。
- 配置与密钥管理、环境隔离和敏感信息保护。
- 数据持久化、备份与恢复的基本思路。
- 服务健康检查、日志查看和常见故障定位。
- 前端访问后端、服务间访问、端口和网络边界。
- 虚拟机资源有限时的模型调用、并发和存储控制。
- 服务重启后会话、任务和数据如何恢复。
- 未来迁移到云服务器或容器平台时需要调整什么。

部署模块不追求企业级运维平台，但必须形成可复现的部署闭环。

## 四、技术选型规划

技术选型原则：优先复用原项目已有基础设施，Python 只新增 Agent 相关能力；选择个人能够掌握、能够在虚拟机中部署、能够在面试中解释清楚的方案。

### 1. 前端

| 部分 | 推荐选型 | 主要原因 |
| --- | --- | --- |
| 页面框架 | 直接复用现有 React + TypeScript + Vite | 已有页面和交互较完整，减少无关重写 |
| HTTP 调用 | 复用现有 Axios 封装 | 保持原有业务接口兼容 |
| Agent 流式输出 | 浏览器原生 SSE 消费 | 适合展示回答、工具状态和任务进度 |
| 实时双向通信 | 首期不作为核心；未来语音场景再使用 WebSocket | 控制首期复杂度 |
| 页面状态 | React 现有状态方案，必要时增加轻量会话状态管理 | 避免引入重量级状态体系 |

### 2. Java 主业务后端

| 部分 | 推荐选型 | 主要原因 |
| --- | --- | --- |
| 业务框架 | 从零构建 Spring Boot 后端 | 深入理解分层架构、业务建模和服务边界 |
| 业务数据 | 从零构建 PostgreSQL 数据访问层 | 深入理解数据模型、事务和持久化 |
| 缓存、锁和任务流 | 从零接入 Redis | 深入理解并发控制、限流和异步任务 |
| 文件存储 | 从零构建对象存储接入 | 完整实现简历和知识库文件链路 |
| Agent 调用 | Java 通过内部 HTTP 接口调用 Python Agent | 保持 Java 作为主业务边界，Python 聚焦智能能力 |
| 接口兼容 | 以现有前端 API 形态为契约，从零实现对应接口 | 前端无需重构，同时后端可独立完成 |

### 3. Python Agent 服务

| 部分 | 推荐选型 | 主要原因 |
| --- | --- | --- |
| Web 服务 | FastAPI | 适合 Python AI 服务、异步调用和流式响应 |
| 数据模型 | Pydantic | 统一请求、工具参数、Agent 事件和结果结构 |
| Agent 编排 | 优先采用 LangGraph；若实际流程较简单，可使用轻量自研状态机 | 能表达 Agent Loop、状态、分支和恢复，同时控制复杂度 |
| LLM 调用 | 采用 OpenAI 兼容接口的统一适配层 | 便于切换阿里云、DeepSeek、OpenAI 兼容服务或本地模型 |
| 配置管理 | 环境变量加配置对象 | 便于虚拟机部署和不同环境切换 |
| 服务间通信 | Java 与 Python 使用内部 HTTP；需要实时结果时使用 SSE | 结构简单，便于调试和演示 |

Python Agent 不管理用户、简历、岗位描述、面试会话和最终业务结果；它负责管理 Agent 运行状态、短期和长期记忆、RAG 索引、检索结果和工具执行记录。Java 通过明确的内部接口提供最小必要业务上下文，Python 通过稳定标识关联用户和会话。

### 4. Agent 能力接入：Tools、Skills 与 MCP

| 能力 | 推荐选型 | 使用范围 |
| --- | --- | --- |
| Tools | Python 函数加 Pydantic 参数模型 | 简历读取、JD 分析、知识检索、出题、评价 |
| Skill | 继续复用 Markdown/YAML 形式的面试方向资料 | 保存角色、规则、知识范围和提问风格 |
| MCP | 使用 Python MCP SDK，首期实现一个可演示的本地或独立能力服务 | 说明标准化外部工具接入，不建设复杂 MCP 生态 |
| 工具注册 | 统一工具注册表 | 让 Agent 看到工具名称、用途、参数和权限边界 |
| 工具结果 | 统一结构化结果 | 支持成功、失败、来源、摘要和下一步判断 |

Tool 是动作，Skill 是知识和行为约束，MCP 是外部能力接入方式。三者需要在代码和面试表达中保持边界清晰。

### 5. RAG 系统

| 部分 | 推荐选型 | 主要原因 |
| --- | --- | --- |
| 原始文件 | 复用 Java 文件管理和对象存储 | 保持现有上传和下载能力 |
| 文档解析 | Python Agent 服务负责 Agent 知识资料的解析 | RAG 数据由 Agent 领域服务完整管理 |
| 文本切分 | Python Agent 服务负责切分和索引 | 便于统一管理检索策略和上下文构建 |
| Embedding | Python Agent 服务通过统一模型适配层调用 Embedding 服务 | 让 RAG 能力与 Agent 保持内聚 |
| 向量存储 | 复用 PostgreSQL + pgvector | 原项目已有基础设施，虚拟机部署成本低 |
| 检索服务 | Python Agent 服务提供检索能力并作为内部 Tool 使用 | Agent 同时决定何时检索和如何使用结果 |
| 来源引用 | 保留文档、段落和片段元数据 | 支持前端展示依据 |
| 质量评估 | 以小规模人工样例和离线测试为主 | 符合实习面试范围，不建设复杂评测平台 |

首期不额外引入独立向量数据库，避免增加虚拟机部署和运维负担。

### 6. 记忆系统

| 记忆类型 | 推荐选型 | 存储/处理原则 |
| --- | --- | --- |
| 当前对话记忆 | Python Agent 会话记忆 | 持久化保存，控制上下文长度 |
| 面试工作记忆 | Python Agent 依据 Java 上下文管理当前阶段、问题和回答摘要 | 与 Agent 执行状态保持一致 |
| 跨会话记忆 | Python Agent 长期记忆 | 以 userId 和 sessionId 进行作用域隔离 |
| 语义记忆 | Python RAG 检索能力 | 不把所有历史内容永久塞入上下文 |
| 上下文压缩 | Python Agent 负责摘要、裁剪和按需检索 | 以信息相关性和 Token 成本为约束 |

首期不引入独立的记忆数据库或复杂记忆框架，优先用会话存储、业务历史和 RAG 组合实现。

### 7. 异步任务与工程可靠性

| 部分 | 推荐选型 | 主要原因 |
| --- | --- | --- |
| 任务队列 | 复用 Redis Stream | 与原项目一致，避免引入 Kafka 等重型组件 |
| 任务消费者 | Java 处理业务任务；Python 处理 RAG 和 Agent 领域任务 | 由数据归属决定任务归属，避免跨服务直接写同一数据 |
| 任务状态 | 数据库状态加任务事件 | 支持前端查询、重试和失败展示 |
| 幂等控制 | 业务唯一键、内容哈希和任务状态校验 | 解决重复上传、重复执行和重复提交 |
| 并发控制 | Redis 分布式锁、会话级约束和全局限流 | 同时覆盖单会话和多用户场景 |
| 失败处理 | 统一错误分类、有限重试、退避和降级 | 避免无限重试和用户无反馈 |
| 运行记录 | Python 持久化 Agent 事件和工具记录；Java 保存业务引用和最终业务结果 | 支持故障排查和面试演示 |

工程化能力以公共组件或中间层形式提供，由具体业务模块调用，不在各业务中重复实现。

### 8. 测试

| 测试范围 | 推荐选型 | 重点 |
| --- | --- | --- |
| Python 单元测试 | pytest | Agent 状态、工具参数、错误分支和 RAG 组装 |
| Python 接口测试 | FastAPI 测试客户端 | Agent 接口、流式事件和错误响应 |
| Java 现有测试 | 继续复用 JUnit 体系 | 保证原有业务不被 Agent 改造破坏 |
| 外部模型测试 | Mock 或固定测试响应 | 避免测试依赖真实 API 和产生额外费用 |
| 全链路验证 | Docker Compose + 固定演示数据 | 验证虚拟机部署后的主流程 |

### 9. 虚拟机部署

| 部分 | 推荐选型 | 主要原因 |
| --- | --- | --- |
| 服务编排 | Docker Compose | 适合单台虚拟机部署多个轻量服务 |
| 前端入口 | 复用现有前端容器和反向代理思路 | 统一访问入口 |
| 后端服务 | Java 服务与 Python Agent 服务分别运行 | 明确职责和独立重启边界 |
| 基础设施 | PostgreSQL、Redis、对象存储按需复用 | 与原项目保持一致 |
| 配置和密钥 | 环境变量或虚拟机本地配置文件 | 禁止将密钥写入代码和镜像 |
| 运行检查 | 健康检查、日志、数据卷和基础备份 | 保证启动、访问和恢复可验证 |

虚拟机部署以可复现、可访问、可验证为标准，不追求完整的企业级运维体系。

## 五、选型边界与待确认项

- 首期不同时引入多个 Agent 编排框架。
- 首期不同时引入独立向量数据库、复杂消息队列和独立记忆数据库。
- Python Agent 与 Java 的数据边界需要在接口设计阶段进一步确定。
- MCP 首期需要选择一个足够小、能够真实演示的接入场景。
- 需要根据虚拟机资源最终确认模型调用、并发和任务数量限制。

## 七、面试重点分配

建议将项目内容分为三个层次：

- 必须讲清：整体架构、面试业务主流程、Agent 基本运行过程、前后端链路和虚拟机部署。
- 重点展开：Agent 编排与工具选择、RAG 检索质量、记忆与上下文管理。
- 能够回答：MCP 与 Skill 的定位、数据一致性、并发控制、失败恢复、异步任务和部署问题。

不要求每个模块都深入实现，但所有模块都必须在架构上有清晰位置，并且不能出现为了面试强行添加、与业务无关的设计。
